`bunny deploy` builds the project in the current directory and publishes it. One command covers both shapes of site:

- A project whose build writes `.bunny/build.json` renders per request in an [Edge Script](/scripting), with its files in [Bunny Storage](/storage). A [framework adapter](https://github.com/BunnyWay/bunny-adapters) writes that file.
- Anything else is a directory of files, which is [`bunny sites deploy`](/cli/commands/sites).

The CLI knows no framework. It reads the manifest the build wrote, so a new adapter needs no new CLI.

```bash
bunny deploy                 # build if needed, then deploy
bunny deploy --build         # run the project's own build first
bunny deploy ./dist          # deploy a directory of files
bunny deploy --open          # open the site when the deploy finishes
```

## Your first deploy

<Steps>
  <Step title="Log in">
    ```bash
    bunny login
    ```
  </Step>

  <Step title="Run the command in your project">
    ```bash
    bunny deploy
    ```

    A framework the CLI recognises with no bunny.net adapter installed gets an offer to add one. The build then runs, the site is created, and the deploy publishes:

    ```
    ℹ Astro detected, with no bunny.net adapter.
    ? Add @bunny.net/astro-adapter to astro.config.mjs? › (Y/n)

    ? Site name: › my-site
    ✓ Created site "my-site".
    ✓ Deployed a1b2c3d4: 42 files (1.9 MB), script 653 KB.
    ℹ Production  https://sites-my-site-k3f9wq.b-cdn.net
    ```

  </Step>

  <Step title="Add your domain">
    The first deploy offers one. To add it later:

    ```bash
    bunny sites domains add www.example.com
    ```

  </Step>
</Steps>

Nothing above asks for a password. The CLI creates the storage zone, so it already holds the credentials. It sets them on the script as [secrets](/scripting/secrets).

## What a deploy creates

| Resource            | What it does                                        |
| ------------------- | --------------------------------------------------- |
| A storage zone      | Holds each deploy's files                           |
| A pull zone         | The site's URL, its cache, and its domains          |
| An Edge Script      | The build's own server, or the static site's router |
| `.bunny/site.json`  | Links this directory to the site                    |

Every deploy goes to its own directory in the storage zone. So publishing an earlier one restores its pages and the files they name, together.

## A build that renders per request

The build writes `.bunny/build.json`, and the CLI acts on it. It uploads the files and publishes the script. It also applies the pull zone settings the adapter asks for, and sets the variables the script reads.

Then it asks the live site for a page. A green line above a URL that answers `400` is the worst thing this command can do. So a script that does not start is reported instead:

```
⚠ The site answered 400, so the script is not serving.
  The script is 8.2 MB, and a script has 500 ms to start. Every byte is parsed first.
  The deploy before it is still there: bunny rollback
```

## A build that renders nothing

A build with no route to render per request writes no script at all. The deploy is the files, and the site is served by the [static sites router](/cli/commands/sites#what-the-deploy-configures): it answers a miss with the build's own `404.html`, and it reads `_redirects` and `_headers` from the deploy.

The build says which of the two it produced, and why.

## Rolling back

```bash
bunny sites deployments list   # what is live, what was live, what is kept
bunny rollback                 # back to the deploy that was live before
bunny rollback a1b2c3d4        # to a named one
```

A rollback reads the earlier deploy's stored bundle back out of storage. So the pages and the files they name come back together.

## Flags

| Flag                        | Description                                                                        |
| --------------------------- | ---------------------------------------------------------------------------------- |
| `--build [cmd]`             | Run a build first. The bare flag uses the project's own build                      |
| `--env K=V`, `--env-file`   | Build-time environment overrides. Only apply with `--build`                         |
| `--name`, `--region`        | Site name and storage region, for the first deploy from this directory              |
| `--force`                   | Deploy even when nothing changed                                                    |
| `--open`                    | Open the site when the deploy finishes                                              |
| `--site`, `--link`          | Target a specific site; link this directory to the site it deploys to               |
| `--prod`, `--production`     | Publish as the live site. A framework build always publishes; a static one needs it |

<Info>
  In a monorepo, run `bunny deploy` at the repository root, and it finds the
  projects below it. Or run it in a project's own directory to deploy that one.
  The package manager comes from the workspace, so a `pnpm` monorepo gets `pnpm`.
</Info>
