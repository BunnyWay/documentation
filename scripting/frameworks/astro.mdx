[Astro](https://astro.build/) is a server-first framework. It renders HTML on the server, and it ships only the JavaScript a page really needs.

The [`@bunny.net/astro-adapter`](https://github.com/BunnyWay/bunny-astro-adapter) package runs that server inside an Edge Script. Astro renders pages and API routes per request, on a node near your visitor. The build's static files come from [Bunny Storage](/storage).

## Set up

<Steps>
  <Step title="Add the adapter">
    In an existing Astro project:

    ```bash
    npx astro add @bunny.net/astro-adapter
    ```

    That installs the package and writes the configuration. To do it by hand:

    ```bash
    npm install @bunny.net/astro-adapter
    ```

    ```js astro.config.mjs
    import { defineConfig } from "astro/config";
    import bunny from "@bunny.net/astro-adapter";

    export default defineConfig({
      output: "server",
      adapter: bunny(),
    });
    ```

  </Step>

  <Step title="Build">
    ```bash
    npm run build
    ```

    The build produces two things:

    | Path | What it is |
    | --- | --- |
    | `dist/index.js` | Astro's server, bundled into the single file Edge Scripting accepts |
    | `dist/client/` | Hashed assets and any prerendered page |

    A small site bundles to roughly 600 kB, against the 10 MB [script size limit](/scripting/limits).

  </Step>

  <Step title="Create a storage zone">
    The zone holds `dist/client`:

    ```bash
    bunny api POST /storagezone --body '{"Name":"my-site-assets","Region":"DE"}'
    ```

    The response carries two passwords. `Password` reads and writes. `ReadOnlyPassword` only reads. Keep both.

    <Note>
      You can also create the zone in the dashboard under **Storage** > **Add
      Storage Zone**, and read the passwords from the **Access** tab.
    </Note>

  </Step>

  <Step title="Create the Edge Script">
    ```bash
    bunny scripts create my-site --type standalone
    ```

    The CLI creates a linked pull zone, which gives the site its URL.

    Point the script at the storage zone. The password is a [secret](/scripting/secrets), and the read-only one is enough because the script never writes:

    ```bash
    bunny scripts env set BUNNY_STORAGE_ZONE my-site-assets
    bunny scripts env set BUNNY_STORAGE_HOST storage.bunnycdn.com
    bunny scripts env set BUNNY_STORAGE_KEY <read-only password> --secret
    ```

    <Note>
      Use the endpoint for your zone's region. The [HTTP
      page](/storage/http#storage-endpoints) lists them all.
    </Note>

  </Step>

  <Step title="Deploy">
    Send the static files, then the server:

    ```bash
    BUNNY_STORAGE_ZONE=my-site-assets \
    BUNNY_STORAGE_KEY=<write password> \
    npx bunny-astro upload

    bunny scripts deploy dist/index.js
    ```

    Open the URL the CLI prints. Reload it, and anything the page renders per request changes each time.

    <Warning>
      Run both commands on every deploy. Astro renames its CSS and JavaScript
      bundles whenever they change, so deploying only the script leaves the new
      names missing from storage, and the site loses its styles.
    </Warning>

  </Step>
</Steps>

## What runs where

| Request | Handled by |
| --- | --- |
| A server-rendered page | Astro, inside the script |
| A route in `src/pages/api/` | Astro, inside the script |
| `src/middleware.ts` | Astro, on every matched route |
| A page with `export const prerender = true` | Bunny Storage |
| Hashed assets in `_astro/` | Bunny Storage |
| An unknown path | Astro's 404 page |

Astro's request context behaves as it does on any server. `Astro.request.headers` carries the bunny.net edge headers, so middleware can read the visitor's country and put it into `Astro.locals`:

```ts src/middleware.ts
import { defineMiddleware } from "astro:middleware";

export const onRequest = defineMiddleware((context, next) => {
  // Middleware also runs while Astro prerenders, where there is no request.
  if (context.isPrerendered) return next();

  context.locals.country = context.request.headers.get("cdn-requestcountrycode") ?? "unknown";
  return next();
});
```

## Supported features

| Astro feature | Supported |
| --- | --- |
| Server-rendered pages | Yes |
| Server endpoints and dynamic routes | Yes |
| Middleware | Yes |
| `Astro.request`, `Astro.locals`, `Astro.url`, `Astro.params` | Yes |
| `Astro.cookies`, including `set()` | Yes, after you allow cookies on the pull zone |
| Prerendered pages | Yes, served from Storage |
| `astro:env` secrets | Yes, from the script's environment variables |
| The `sharp` image service | No. The adapter swaps in the no-op service |

## Cookies

A pull zone created for a script has **Disable cookies** switched on, and it strips `Set-Cookie` from every response. Turn it off before `Astro.cookies.set()` reaches the browser:

```bash
bunny api POST /pullzone/<pull-zone-id> --body '{"DisableCookies": false}'
```

`bunny scripts show <script-id>` prints the linked pull zone and its ID.

## Adapter options

Every option has a sensible default, so `bunny()` on its own is usually right.

```js astro.config.mjs
bunny({
  storageZone: "my-site-assets",  // otherwise read from BUNNY_STORAGE_ZONE
  storageHost: "ny.storage.bunnycdn.com", // otherwise BUNNY_STORAGE_HOST
  outfile: "dist/index.js",       // where to write the deployable bundle
  bundle: true,                   // false to run your own bundler
  imageService: "noop",           // false to keep your own image service
  assetCacheControl: "public, max-age=31536000, immutable",
  pageCacheControl: "public, max-age=60",
});
```

The storage password is never an option. It always comes from the environment, so it stays out of the bundle.

## Run it locally

Use `npm run dev` for everyday work on the site.

To exercise the real edge bundle, build it and run it with [Deno](https://deno.com/):

```bash
npm run build
BUNNY_STORAGE_ZONE=my-site-assets \
BUNNY_STORAGE_HOST=storage.bunnycdn.com \
BUNNY_STORAGE_KEY=<read-only password> \
deno run -A dist/index.js
```

It listens on `http://127.0.0.1:8080/` and reads the assets from the real zone. The `cdn-` headers only exist on the bunny.net network, so anything your code reads from them is absent locally.

## Add your own domain

The script has a pull zone, so it takes a custom hostname:

```bash
bunny scripts domains add www.example.com
```

Point the hostname at bunny.net with a `CNAME` record, then enable HTTPS. See the [custom hostname guide](/cdn/custom-hostname).

## A static site instead

If the site has no dynamic part, you do not need a script at all. Keep Astro's default `static` output, upload `dist/` to a storage zone, and point a pull zone at it. The [frontend deployment guides](/storage/static-site-hosting) cover that path.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Prerendered pages return 404">
    Upload `dist/client` again. Astro writes those pages to
    `dist/client/<route>/index.html`, and the adapter looks for both
    `<route>/index.html` and `<route>.html`.
  </Accordion>

  <Accordion title="Assets 404 but pages render">
    Only `dist/client` belongs in storage. Uploading `dist` instead puts every
    asset one level too deep. `bunny-astro upload` reads the right folder by
    default.
  </Accordion>

  <Accordion title="The site loses its styles after a deploy">
    The script was deployed without a fresh upload. Astro renames its CSS
    bundle whenever the styles change, so the new name is missing from storage.
    Run `bunny-astro upload` and deploy again.
  </Accordion>

  <Accordion title="Astro.cookies.set() has no effect">
    The pull zone is stripping the header. Turn off **Disable cookies**, as
    described above.
  </Accordion>

  <Accordion title="A POST request returns 403">
    Astro checks the request origin for server output, and rejects a form POST
    whose `Origin` header does not match the site. This is Astro's CSRF
    protection, not an Edge Scripting error. Send the request from the site
    itself, or change `security.checkOrigin` in `astro.config.mjs`.
  </Accordion>

  <Accordion title="The bundle fails on child_process, fs, or detect-libc">
    A dependency needs Node-only modules. The adapter already replaces the
    `sharp` image service, which is the usual cause. If another dependency does
    it, replace that dependency or keep it out of the server build.
  </Accordion>

  <Accordion title="Every request returns a storage error">
    Check that `BUNNY_STORAGE_ZONE` matches the zone name, that
    `BUNNY_STORAGE_KEY` is a password of that zone, and that
    `BUNNY_STORAGE_HOST` matches the zone's region. A zone created seconds ago
    can answer `401` until it propagates.
  </Accordion>

  <Accordion title="The script is too slow to start">
    A script has 500 ms to start. Move work out of module scope and into the
    request handler, and drop dependencies you do not need. Check the size of
    `dist/index.js` against the [limits](/scripting/limits).
  </Accordion>
</AccordionGroup>
