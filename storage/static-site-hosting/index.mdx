A static site on bunny.net is a storage zone that holds your built files, with a pull zone in front that serves them from the CDN. You can set that up with the [Bunny CLI](/cli), which detects your framework, runs the build, and uploads the output, or you can create the zones in the dashboard and upload the files yourself.

## Deploy with the Bunny CLI

<Warning>
  `bunny sites` is experimental and available only in the Bunny CLI. Commands,
  flags, and behaviour may change, so [open an
  issue](https://github.com/BunnyWay/cli/issues) if something breaks. The
  storage zone and pull zone behind each site appear in the dashboard under
  **Storage** and **CDN**.
</Warning>

From your project root:

```bash
bunny sites create my-site
bunny sites deploy --build
```

`bunny sites create` makes the storage zone and pull zone and links your directory to the site. `bunny sites deploy --build` detects your framework, runs its build with the package manager from your lockfile (Bun, pnpm, Yarn, or npm), and publishes the output directory. Each deploy is kept, so `bunny sites deployments publish --previous` rolls back to the last one.

Run `bunny sites ci init` to add a GitHub Actions workflow that deploys on every push to `main`. See [`bunny sites`](/cli/commands/sites) for every command.

### Site configuration

When detection doesn't fit your project, add a `sites` block to `bunny.jsonc` at your project root. Every field is optional:

```jsonc bunny.jsonc
{
  "sites": {
    "name": "my-site",
    "build": "npm run build",
    "dir": "dist",
    "spa": true
  }
}
```

| Field   | Description                                                                 |
| ------- | --------------------------------------------------------------------------- |
| `name`  | The site this directory deploys to                                          |
| `build` | The command `bunny sites deploy --build` runs                               |
| `dir`   | The directory to deploy, relative to `bunny.jsonc`                          |
| `spa`   | Serve `index.html` for unknown paths, for apps with client-side routing     |

`bunny sites ci init` reads the same file, so GitHub Actions builds and deploys what you deploy locally.

## Single-page apps

Single-page apps (React, Vue, Angular, and others) handle routing in the browser. When someone opens a deep link such as `/dashboard` or refreshes the page, the request has to return `index.html` so the router can take over.

The Bunny CLI sets this up for frameworks that build single-page apps, and asks when a build looks like one. For a manual deploy, configure your storage zone:

<Steps>
  <Step title="Open your storage zone">
    In the [bunny.net dashboard](https://dash.bunny.net), go to **Storage** and select your storage zone.
  </Step>
  <Step title="Open Error handling">
    Open the **Error handling** page.
  </Step>
  <Step title="Serve index.html for missing paths">
    Enter `/index.html` in the **404 File path** field, check **Rewrite 404 to 200 status code**, and click **Save**.
  </Step>
</Steps>

Requests for missing files with an extension, such as `.js`, `.css`, or images, still return a 404. See [Storage zone settings](/storage/settings#error-handling) for details.

## Resize images with Bunny Optimizer

[Bunny Optimizer](/optimizer/dynamic-images/overview) resizes images at the edge from query parameters such as `?width=640`, so your build can ship one copy of each image.

<Optimizer />

The [Next.js](/storage/static-site-hosting/nextjs#resize-images-with-bunny-optimizer), [Nuxt](/storage/static-site-hosting/nuxt#resize-images-with-bunny-optimizer), [Astro](/storage/static-site-hosting/astro#resize-images-with-bunny-optimizer), and [Angular](/storage/static-site-hosting/angular#resize-images-with-bunny-optimizer) guides plug Optimizer into each framework's image component. Anywhere else, write the `srcset` yourself:

```html
<img
  src="/images/photo.jpg?width=1200"
  srcset="/images/photo.jpg?width=640 640w, /images/photo.jpg?width=1200 1200w"
  sizes="100vw"
  alt="Photo"
/>
```

## Cache configuration

Static frontends benefit from long cache times on assets. Consider these settings in your pull zone:

| File type       | Recommended cache time              |
| --------------- | ----------------------------------- |
| HTML            | Short (1 hour) or use cache busting |
| JS/CSS (hashed) | Long (1 year)                       |
| Images          | Long (1 month+)                     |
| Fonts           | Long (1 year)                       |

<Note>
  Build tools such as Vite add content hashes to filenames (for example,
  `main.a1b2c3.js`), so these files are safe to cache indefinitely.
</Note>
