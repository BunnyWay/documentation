Static site hosting on bunny.net is two resources working together. A Storage Zone holds your build output, and a Pull Zone serves it from every edge location. There's no server to run and nothing to keep warm, because the CDN answers every request.

## Choose how to deploy

<CardGroup cols={2}>
  <Card title="Bunny CLI" icon="terminal" href="/storage/static-site-hosting/bunny-cli">
    Run `bunny sites` to create both zones, deploy in one command, and roll back
    to any earlier deploy.
  </Card>
  <Card title="Manual setup" icon="sliders" href="/storage/static-site-hosting/manual-setup">
    Create the Storage Zone and Pull Zone yourself, upload with the API of your
    choice, and control every setting.
  </Card>
</CardGroup>

|                        | Bunny CLI                                       | Manual setup                                  |
| ---------------------- | ----------------------------------------------- | --------------------------------------------- |
| Create the zones       | `bunny sites create`                            | Dashboard or Core API                         |
| Deploy a build         | `bunny sites deploy ./dist`                     | Upload over HTTP, S3, or FTP                  |
| Preview URL per deploy | Yes                                             | No                                            |
| Roll back              | `bunny sites deployments publish --previous`    | Re-upload the previous build, then purge      |
| Cache after a deploy   | Purged automatically                            | [Purge it yourself](/cdn/purge-cache)         |
| Client-side routing    | Not built in                                    | Error handling on the Storage Zone            |
| Zone settings          | Managed for you                                 | Yours to configure                            |

Both approaches produce the same thing: files in Bunny Storage, served through a Pull Zone. You can start with the CLI and still open the zones it created in the dashboard.

## Client-side routing

Single-page applications handle routing in the browser. When someone opens `/dashboard` directly, bookmarks `/products/123`, or refreshes on `/settings`, the request reaches the CDN as that exact path. Only `index.html` and your assets exist in storage, so the response is a 404 unless you tell the Storage Zone to fall back to `index.html`.

<Steps>
  <Step title="Open your storage zone">
    Go to **Storage** in the [dashboard](https://dash.bunny.net) and select your
    storage zone.
  </Step>
  <Step title="Open Error handling">
    Open the **Error handling** page.
  </Step>
  <Step title="Set the 404 file path">
    Enter `/index.html` in the **404 File path** field.
  </Step>
  <Step title="Enable the 404 to 200 rewrite">
    Check **Rewrite 404 to 200 status code** and click **Save**.
  </Step>
</Steps>

Missing paths now serve `index.html` and your router takes over. Requests for files with an extension, such as `.js`, `.css`, or an image, still return a 404, so a broken asset reference stays visible instead of silently returning HTML.

<Warning>
  Sites created with `bunny sites` store each deploy in its own directory, so a
  zone-wide 404 path can't point at the live deploy's `index.html`. Use the
  manual setup for single-page applications that rely on history-mode deep
  links.
</Warning>

<Info>
  See [Storage Zone Settings](/storage/settings#error-handling) for the full
  error handling reference.
</Info>

## Custom domains

Both approaches serve your site on a `b-cdn.net` hostname straight away. To use your own domain, add it as a hostname on the Pull Zone and enable Free SSL. See [Custom Hostname](/cdn/custom-hostname), or run `bunny sites domains add example.com --wait` to do the same from the terminal.

## Cache configuration

Static builds cache well. Set these cache times on the Pull Zone:

| File type       | Recommended cache time              |
| --------------- | ----------------------------------- |
| HTML            | Short (1 hour) or use cache busting |
| JS/CSS (hashed) | Long (1 year)                       |
| Images          | Long (1 month or more)              |
| Fonts           | Long (1 year)                       |

<Note>
  Build tools like Vite add a content hash to filenames, such as
  `main.a1b2c3.js`. Hashed files are safe to cache indefinitely, because a new
  build produces a new filename.
</Note>

Bunny CDN doesn't watch your origin for changes. After overwriting a file that's already cached, [purge the cache](/cdn/purge-cache) so visitors see the new build.
