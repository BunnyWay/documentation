Server-Sent Events (SSE) is a one-way stream of text from a server to a client. The server keeps the HTTP response open and writes events into it, and the client reads them with the [EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource) API. Applications use it for live dashboards, progress updates, notifications, AI token streams, and MCP servers.

Bunny CDN supports SSE. There is no setting to enable, because an event stream is a standard HTTP response with the `text/event-stream` content type. The edge streams each event to the client as soon as your origin writes it.

SSE works with every origin type:

- Your own origin server.
- [Edge Scripting](/scripting/server-sent-events), which streams events from a script.
- [Magic Containers](/magic-containers/endpoints#cdn), through a CDN endpoint.

Four rules keep a stream healthy on the edge network:

- **Send `Cache-Control: no-cache`.** Without it the edge caches the stream, and later clients receive a recording of it instead of live events.
- **Send the first event immediately.** Nothing reaches the client before the first byte.
- **Send data at least every 30 seconds.** The edge closes a stream that carries no data for approximately two minutes.
- **Let the client reconnect.** We promise no maximum duration, and a closed stream ends with a connection error, not with a clean end of the response.

The sections below explain each rule.

## Send the first event immediately

<Warning>
  Send the first event as soon as the connection opens, and do not wait for the
  first real update. With [Edge Scripting](/scripting/server-sent-events), the
  client receives no part of the response until the script writes the first
  byte, and this includes the response headers. Until that byte arrives, a
  healthy stream looks the same as a connection that failed.
</Warning>

An event that carries the current state works well as the first event. A comment line, or an event with an empty payload, is sufficient when you have no state to send.

## Keep the stream active

The edge closes a connection that carries no data for approximately two minutes. This is the only duration limit that applies to an event stream. As long as data flows, the connection stays open.

Send a heartbeat at least every 30 seconds when you have no events to deliver. An SSE comment line is sufficient, because the client ignores it:

```text
: heartbeat

```

The heartbeat resets the timer because it is real data on the connection. It does not matter whether the bytes are an event or a comment.

<Warning>
  We do not guarantee a maximum connection duration. An edge server can close a
  stream at any time, for example during maintenance. The client sees a
  connection error, not a clean end of the response, so always let the client
  reconnect.
</Warning>

A closed stream does not look like a finished response, and what your client reports depends on the protocol version:

- Over HTTP/2, the stream is reset. A client library usually reports a stream or connection error.
- Over HTTP/1.1, the chunked body simply stops. A client library usually reports an unexpected end of the response.

`EventSource` in a browser handles both the same way: it reports an error and reconnects on its own.

Give each event an `id` field. After a disconnect, `EventSource` reconnects automatically and sends the last identifier in the `Last-Event-ID` request header, which lets your origin continue from that point:

```text
id: 42
event: price
data: {"symbol":"BUNNY","value":128.4}

```

## Keep the event stream out of the cache

<Warning>
  **Send `Cache-Control: no-cache` from your origin.** This is required, not a
  recommendation. An event stream is cached like any other response, and an
  origin that sends no `Cache-Control` gets the pull zone's default cache time,
  which is 1 month.
</Warning>

A cached stream stops being a stream. The first client fills the cache, and every client after that receives the whole recorded body at once, carrying the first client's data, followed by the end of the response. The browser then reconnects, receives the same recording again, and loops.

Keep the stream out of the cache:

- Send `Cache-Control: no-cache` from your origin. Bunny follows this header and does not cache the response.
- Do not apply an [Override Cache Time](/cdn/edge-rules/custom-cache-time) Edge Rule to the path that serves the stream. A cache time override applies to an event stream as well.
- Check the **Ignore Query Strings** setting on your pull zone. While it is on, the cache key is the path alone, so one cached body answers every query string. A per-user stream selected by a query parameter would then be served to every user.

An [Edge Script](/scripting/server-sent-events) that returns the stream itself needs none of this. A standalone script response is never cached.

If you use [Request Coalescing](/cdn/request-coalescing), give each client its own URL, for example with a session or user query string parameter. Coalescing joins simultaneous requests for the same URL into one origin request, which is correct for a shared feed, but not for a per-user stream.

## Origin requirements

- Send the response headers immediately. Bunny waits 60 seconds for your origin to start the response, and returns a `504 Gateway Timeout` with error code `106` if nothing arrives. This limit applies only until the headers arrive, and not to the stream that follows, however long it runs. See [502 and 504 errors](/cdn/connectivity#502-and-504-errors).
- Write and flush each event immediately. Output buffering in your framework or your origin web server holds events back, and the client receives them late or in one block.
- Remove any request time limit on the origin route that serves the stream.

## Costs and limits

An event stream is a standard HTTP request, and it uses the standard request pipeline. Bunny bills the data it transfers at the [normal CDN bandwidth rate](/cdn/pricing). The [WebSocket connection limits](/cdn/websockets#connection-limits) and the WebSocket connection-time price do not apply to an event stream.

If an [Edge Script](/scripting/server-sent-events) produces the stream, the script also bills [CPU time and requests](/scripting/pricing). It does not bill the time the connection stays open.

## SSE or WebSockets

| Use SSE when                                    | Use [WebSockets](/cdn/websockets) when              |
| ----------------------------------------------- | --------------------------------------------------- |
| Only the server sends data.                     | The client and the server both send data.           |
| Text events are sufficient.                     | You need binary frames.                             |
| You want automatic reconnection in the browser. | You control reconnection in your own client.        |
| You want plain HTTP, with no setting to enable. | You accept a per-zone connection limit and a separate price. |
